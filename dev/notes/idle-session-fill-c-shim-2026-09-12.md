# Idle-session silence fill in the C shim: research note (2026-09-12)

Problem: a receiver (Sonos Move seen live) closes its RTSP session about 30 s after a session connects with no audio packets. The whole-system tap idles until an app plays, so nothing is written until then. Removing `kAudioAggregateDeviceTapAutoStartKey` fixes it at a permanent coreaudiod cost the owner rejected. The chosen direction keeps the tap idling and feeds silence from the shim. This note checks that direction against primary sources. Paths are repo-relative; upstream line numbers are from the commits named in section 3 to 5.

## (a) Verdict

Build the fill in `shims/outputs.c` as a persistent 8 ms libevent timer on `evbase_player`, created and freed beside the dispatcher's existing deferred event. It writes zeroed S16 PCM straight into `output_airplay.write` / `output_raop.write` (not through `outputs_write`, so host-write bookkeeping stays honest) for every distinct `stream_id` that has at least one device with a live session and `device->state` at `OUTPUT_STATE_CONNECTED` or `STREAMING`, once the host has been quiet for 100 ms. It stamps `pts` continuing from the last delivered end-pts, capped at now minus one packet, and writes exactly the samples owed by elapsed time. Nothing in `AirPlayEngine.swift` needs to change beyond a comment; no vendored file changes. The previous sketch holds; the two corrections are that stream discovery should come from the shim's own device registry (the sender's session lists are file-static), and that pts discontinuities at handover have no receiver-visible effect in this build because periodic sync packets are compiled off.

## (b) Answers

**1. Write path and structs.** `write(streams:pts:)` (`AirPlayEngine/Sources/AirPlayEngine/AirPlayEngine.swift:1173`) copies each buffer, records cadence (1198), backpressure (1219), level (1259), then builds a stack `output_buffer` with `pts` and one `output_data` per entry (`quality`, `buffer`, `bufsize`, `samples`, `stream_id`; 1304-1318) and calls `outputs_write(&obuf)` (1320). Struct layout: `shims/outputs.h:172-192`; the array is NULL-terminated, each backend loops `for (i; obuf->data[i].buffer; i++)`. Format is interleaved S16LE 44100/2 (`airplay.c:4182-4184` device defaults; the master session is keyed on that quality, `airplay.c:1167-1180`). `outputs_write` broadcasts to both backends (`shims/outputs.c:319-325`). `airplay_write` (`sender/airplay.c:4341`) skips entries whose `stream_id` or quality do not match the master session (≈4359-4362), calls `timestamp_set(ams, obuf->pts)` (4364), `packets_sync_send` (4367), appends to `input_buffer`, and sends one packet per 352 samples (`AIRPLAY_SAMPLES_PER_PACKET`, 85) via `packets_send` (4379). `raop_write` mirrors this (`sender/raop.c:4713-4770`).

pts semantics: the audio packet's rtptime is `rtp_session->pos`, a running sample counter (`sender/rtp_common.c:167`, advanced at 186). `pts` never touches it. `timestamp_set` (`airplay.c:2232-2258`) only stores `cur_stamp.ts = pts` and `cur_stamp.pos = pos + input_buffer_samples - output_buffer_samples`; that pair is used solely by sync packets. Sync packets go to a session at `CONNECTED` once (init sync, 2289-2293) and to `STREAMING` sessions only when `rtp_sync_is_time` (2270, 2299-2302), which is never true here: both `rtp_session_new` calls pass `sync_each_nsamples = 0` (`airplay.c:1194`, `raop.c:1913`; `rtp_common.c:229-237`). So a pts discontinuity affects only the anchor a *joining* device receives; an already-streaming session sees a contiguous rtptime stream regardless of pts.

**2. Thread and event base.** The engine thread runs `event_base_dispatch` (`EngineThread.swift:238`); `evbase_player` is set to that base before `airplay_init` (`AirPlayEngine.swift:419`) and both senders create their keep-alive timers on it (`airplay.c:4423`, `raop.c:4856`). `outputs_write` runs inside the enqueued body, which `event_base_once` fires on the engine thread (`EngineThread.swift:294`), or inline when already on it (266-269), or inline in headless mode (`AirPlayEngine.swift:1335`). The shim's registry is engine-thread-only (`shims/outputs.c:45-48`). A libevent timer callback on the same base runs on the same thread, so it may call the backends' `write` directly, no marshalling, no lock. Existing pattern: the persistent no-op timer `event_new(b, -1, EV_PERSIST, ...)` + `event_add` (`EngineThread.swift:228-233`); in C, the dispatcher's `evtimer_new(evbase_player, deferred_cb, NULL)` created in `outputs_dispatcher_init` and freed in `outputs_dispatcher_deinit` (`shims/outputs.c:699-723`), which `start()`/`stop()` already bracket (`AirPlayEngine.swift:422`, `585`).

**3. Upstream OwnTone on pause** (owntone/owntone-server master c51748a5, 2026-07-29). `playback_pause` sends `outputs_flush` (`src/player.c:2477-2497`); the flush callback then arms `outputs_device_stop_delayed` (`src/player.c:1569-1596`), a 10 s timer (`OUTPUTS_STOP_TIMEOUT 10`, `src/outputs.c:89`; `stop_timer_cb` → `outputs_device_stop`, 251-257; armed at 985-997) that tears the session down; resuming cancels it (`pb_timer_start`, 1685-1692). So upstream never holds an idle session open longer than 10 s and never relies on the keep-alive for idling. While *playing* with the input exhausted it does stream silence (`source_read`, `src/player.c:1197-1226`, "Stream silence if playback didn't end yet"). The keep-alive timer is identical to ours (`src/outputs/airplay.c:113`, 1891-1909, armed only in `airplay_write` at 4273-4278). Conclusion: "feed silence while a session is meant to stay open" is the reference behaviour; keep-alive-without-audio is not something upstream ever exercises.

**4. Receiver idle timeouts.** shairport-sync (mikebrady/shairport-sync master 7bad231c, 2026-09-09): the only session timeout is TCP keepalive on the RTSP socket, `config.timeout` default 60 s (`shairport.c:507`, `2472`; `rtsp.c:4556-4630`). `time_of_last_audio_packet` is written (`player.c:1497`, reset 3597) but never read for a timeout. `handle_feedback` (`rtsp.c:2033-2082`) replies with the stream list and touches no timer. openairplay/airplay2-receiver (6c343d36) likewise: `handle_feedback` returns stream descriptors (`ap2-receiver.py:907-937`), TCP server timeout 60 s (1238). Neither open-source receiver drops a session for missing audio. Sonos: no primary source found; the 30 s drop is a live observation only, and whether `/feedback` alone would hold it is unverified.

**5. AirPlay 2 keep-alive.** The vendored keep-alive is `POST /feedback` (`airplay.c:1833-1836`, table 3808) every 25 s (113), armed only by `airplay_write` on the CONNECTED→STREAMING edge (4392-4393). AirPlay 1: `raop_metadata_keep_alive_send` returns 0 unless `rs->wanted_metadata && raop_cur_metadata` (`raop.c:2682-2690`); `raop_cur_metadata` is set only by `raop_metadata_send` (2716), which nothing in shims or Swift calls, and the metadata path is cut (`shims/db.h:41`). So on AirPlay 1 there is no keep-alive at all; audio is the only thing that can hold a session. pyatv (postlund/pyatv master b277a4c8) sends `/feedback` every 2 s on AirPlay 2 (`pyatv/protocols/raop/protocols/airplayv2.py:25`, 172-181; `pyatv/protocols/airplay/ap2_session.py:29`) and every 25 s on AirPlay 1 if the first `/feedback` returns 200 (`airplayv1.py:16`, 87-109), commented "to ensure connection is not closed by remote device" (`stream_client.py:430`). emanuelecozzi.net AirPlay 2 notes (archived copy, "POST /feedback"): "Probably an heartbeat to ensure the receiver is alive. Sent until the receiver is disconnected." No primary source states that feedback without RTP keeps an Apple or Sonos session open, and today's idle sessions never sent one: the timer is armed only by a write, so an idle session stayed at CONNECTED with no feedback at all. Whether feedback alone would hold a Sonos session is untested. Silence is the only path that works on both protocols.

**6. Test seams.** `enterHeadlessTestMode` (`AirPlayEngine.swift:1674`) runs writes inline with no event base, so a libevent timer cannot fire in tests; a `_tick_for_test(now)` entry is required. `MultiStreamWriteRoutingTests` (98-299) drives the real Swift write into real master sessions via `airplay_test_master_session_make` / `_input_buffer_samples` (`shims/engine_bridge.h:141-165`), staying under one packet so `packets_send` is never reached (header, lines 18-24). `ShimUnitTests:324-385` already runs the ffmpeg ALAC encoder headless on full packets, and `packets_send` with an empty `airplay_sessions` list only encodes and commits (`airplay.c:2183-2216`), so a full 352-sample fill packet is safe headless. `StreamLevelTests` (41-80) and `WriteBacklogTests` (43-169) test the Swift trackers alone. `device->state` is written only by the shim's drain (`shims/outputs.c:563`, `609`), and `device->session` by `outputs_device_session_add` (214), so a test can seed both fields on a registry device directly. Live: `dev/fake-speakers.sh` runs shairport-sync (line 5, 23), AirPlay 1 only (`dev/AGENTS.md:11`), and shairport-sync never drops on silence (answer 4), so the fake proves only "fill packets are accepted"; the timeout proof needs the Sonos.

**7. PTP clock gate.** Every `addOutput` goes through `ensurePTPTakeover` (`NativeBackend.swift:6459-6510`), which peeks `willWaitForClock` (`PTPHelperService.swift:297`) and awaits `activate` before the engine session is created. The fill only acts on devices with a session and a connected state, and `session_make` binds the master session with `use_ptp` decided then (`airplay.c:1710`). So silence cannot start before the clock decision, and no change is needed.

**8. Write guards.** Bypass them. `WriteBacklogGuard` (`AirPlayEngine.swift:2126`), cadence (1198), latency (1204), level (1259) and `stream_health` (`NativeBackend.swift:8304-8313`, whose `silent_s`/`writes` are documented as host-side truth, `AudioutCore/Sources/AudioutCore/AGENTS.md:24`) all sit above `outputs_write`; a C-side fill never enters them, so "writes" keeps meaning host writes. What changes: the cadence tracker's claim that cumulative deficit equals receiver-visible shortfall (1189-1196 comment) is no longer true while the fill runs; one comment line fixes that. Passing the fill through the Swift guards instead would inflate `writes`, zero `silent_s`, and cost a heap copy per tick for nothing.

**9. Handover.** Fill has written through pts_f = now − 8 ms; the host's first buffer carries pts_h = now − 10..30 ms (IOProc `mHostTime` rebased to CLOCK_MONOTONIC, `NativeCaptureCoordinator.swift:3682-3691`). Overlap in pts terms: 2 to 22 ms backwards. Receiver effect on a streaming session: none, because rtptime is `pos` and periodic sync is off (answer 1); the host's samples are appended contiguously after the fill's. What does change is buffered lead: the fill kept delivered samples equal to elapsed time, so the host's first buffer adds its own 10-30 ms once; the receiver's 2250 ms start buffer (`shims/outputs.h:251`, `airplay.c:1229`) absorbs it. A device joining within that one tick gets an init sync anchored 2-22 ms early, well inside the 250 ms minimum latency (`airplay.c:94`). No audible artefact is expected; unverified by ear.

## (c) Edit list

- `AirPlayEngine/Sources/CAirPlayEngine/shims/outputs.c` (~80 lines): per-stream table `{stream_id, last_host_write_mono, end_pts}`; in `outputs_write` stamp both from each entry (`end_pts = pts + samples/44100`); `idle_fill_tick(now)`: scan `device_list` for devices with `session != NULL` and state CONNECTED/STREAMING, seed unknown streams at `end_pts = now − 352/44100`, and for each stream idle ≥ 100 ms write `n = floor(((now − 1 packet) − end_pts) × 44100 / 352)` packets of zeros (cap n at 32) with `quality = device->quality`, calling `output_raop.write` and `output_airplay.write` directly, then advance `end_pts`; persistent 8 ms `evtimer` created in `outputs_dispatcher_init`, freed in `outputs_dispatcher_deinit`; drop table entries whose stream has no live device.
- `AirPlayEngine/Sources/CAirPlayEngine/shims/engine_bridge.h` (~8 lines): `int outputs_idle_fill_tick_for_test(struct timespec now)` returning samples written, and `struct timespec outputs_idle_fill_end_pts_for_test(uint32_t stream_id)`.
- `AirPlayEngine/Sources/AirPlayEngine/AirPlayEngine.swift` (~2 lines): amend the cadence comment at 1189-1196.
- `AudioutCore/Sources/AudioutCore/NativeCaptureCoordinator.swift:3574-3579` and `AudioutCore/Sources/AudioutCore/AGENTS.md:23`: restore `kAudioAggregateDeviceTapAutoStartKey` (revert the capture half of 7093048c); `PerAppCaptureCoordinator.swift:1239` already keeps it.

## (d) Test plan

New `AirPlayEngine/Tests/AirPlayEngineTests/IdleSilenceFillTests.swift`, nested under `SerializedEngineState` like `MultiStreamWriteRoutingTests` (~60 lines), each with a real master session and a registry device seeded with `session` and `state`:
- `noFillWhileHostWroteWithin100ms`: write via the Swift API, tick at +50 ms, expect 0 samples.
- `fillWritesSamplesOwedByElapsedTime`: tick at +108 ms, expect 12 packets (4224 samples), `end_pts` advanced by exactly that; second tick +8 ms later writes 352.
- `fillSkipsStreamsWithoutConnectedDevice`: state `STARTUP` or `session == NULL`, expect 0.
- `hostWriteStopsFillImmediately`: after fill, one host write, tick at +8 ms, expect 0.
Run: `bash scripts/run-tests.sh --filter IdleSilenceFillTests`, then `--filter MultiStreamWriteRoutingTests` and `WriteBacklogTests`; confirm the "Test run with N tests" line.

Live proof (dev bundle id, live-test slot): select the Sonos Move with nothing playing, wait 120 s, expect no session drop in telemetry and `engine.log` showing feedback armed; then start playback and listen at the handover; repeat with pause/resume gaps of 5 s and 60 s. Check Activity Monitor: coreaudiod at idle level while the speaker is selected. Fake speaker (`dev/fake-speakers.sh`) only confirms AirPlay 1 packets are accepted with the host silent.

## (e) Risks and unverified

- Sonos's timeout rule and whether feedback alone would hold it: no primary source; live only.
- Audibility of the handover and of a 100 ms fill burst after a long stall: not tested by ear.
- F-REANCHOR flush (`NativeBackend.swift:5549-5560`) sets a session back to CONNECTED (`airplay.c:3359-3363`); the fill's next tick re-anchors it before the rebuilt tap does. Same clock, same math, but unproven live.
- `device->state` lags `session->state` by one deferred drain (`shims/outputs.c:371-375`); the fill may start a tick late. Harmless.
- A fill burst runs ALAC encode for up to 32 packets in one tick on the engine thread; not measured.
- Per-app streams: the mixer writes at stream ≥ 1 and its taps keep the auto-start key; the fill covers them too, which is intended, but per-app idle behaviour was not part of today's live check.
