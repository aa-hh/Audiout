# AudioutPopoverUI

## Purpose

The menu-bar popover UI (pure AppKit), and — since U3 — the **one-surface host**: `AppSurfaceController` owns the single `ControlPanelWindowController` shell and swaps three screens through it (Mixer = the real popover panel, Groups, Settings) behind the header's tab-bar switcher. `PopoverController` owns the Mixer brain, builds the card stack, ingests `Device` snapshots via `update(devices:)`, and drives `GroupController`/`AppRoutingController`. Routing arithmetic lives in Core (see [../../AGENTS.md](../../AGENTS.md)); this folder only renders and turns clicks into controller calls. Shared row views live in [../AudioutSharedUI/](../AudioutSharedUI/). This target depends on `AudioutWindowUI` + `AudioutSettingsUI` (the surface composes their content) — neither may ever depend back on it.

## Rules

- Reacts only to `Device.connectionState` EDGES, not polling: `→ .failed` auto-expands its diagnosis panel once per episode; `guess → diagnosed` is the same episode and must not re-run cleanup. `→ .failed` does NOT drop the device from Selected Devices / a group (R12, W2-T3 — keep intent, always) — the silence watchdog covers audibility, and the backend auto-reconnects when the device GENUINELY comes back (a changed-descriptor re-resolve, a reappear-after-`disappeared`, or an engine good-state transition — since the 2026-08-06 storm fix a same-descriptor re-announce of a dead receiver deliberately does NOT re-kick; the user's "Try again"/re-toggle covers that case).
- Diagnosis panels auto-drive off `.failed` edges — `openDiagnosisIDs` is the open intent; a user ✕ records into `dismissedDiagnosisIDs` for the current episode, so no repaint/rebuild or mid-episode re-report resurrects a dismissed panel. A fresh `→ .failed` edge is a NEW episode: it clears the dismissal and re-expands. "Try again" is `GroupController.retryConnection` → `OutputBackend.retryOutput` — a single-device re-kick, never a membership edit and never a broad routing re-apply (a re-apply used to re-kick EVERY parked `.failed` id — the 2026-08-06 retry storm; a membership-neutral `setOutputSet` is no longer a retry). **The backend upholds the episode boundary**: its autonomous recovery (discovery re-kick on a genuine came-back edge, requeues) deliberately never emits `.connecting` for a `.failed` device — only user-initiated attempts (retry / toggle edge) and wake reconnects do — so a fresh `.failed` edge here always means a NEW deliberate attempt, and a dismissed panel can never be resurrected by background retry cycles. Don't "fix" the backend into showing a spinner for autonomous retries without revisiting this rule.
- **The open intent is ALSO pruned against MEMBERSHIP, not only against connection-state edges** (live bug, 2026-08-06). `.failed` is STICKY: deselecting a failed device produces no `→ .off` edge, so an edge-only rule left the panel mounted under a row the user had explicitly unselected, for the rest of the session. `handleConnectionTransitions` drops both intent sets for any id that fails `wantsAudio(_:)` (selected member OR app-redirect target — deliberately NOT `applySelectionState`'s `controllable:`, which is group-aware via `isMainOutMember`). This is the MIRROR of R12 above, not a breach of it: R12 forbids a FAILURE from dropping the user's selection; this drops the failure REPORT when the USER drops the selection.
- Every delegate callback mutates then calls `rebuild()`; rows aren't mutated in place after a structural change, except the refreshers used for mid-open repaints.
- Collapse state is keyed by the exact card header string — collapse calls must pass the same title the card was built with. The device-type SUBSECTIONS ("This Mac" / "AirPlay Devices" / "Cast Devices" / "Bluetooth Devices", in that shipped order) ride the identical `collapsedState(for:default:)` machinery under their own titles, so the two rebuild flavors below govern them too.
- **A subsection collapses by animating its OWN clip's height, never by rebuilding** (live report, 2026-08-10 — the drawer read right while sections "snapped/juddered"). Its rows live in a `SubsectionBody` clip and travel on the one shared `collapseRevealDuration` (bullet below). A `rebuild()` toggle put the content at its final height INSTANTLY and left only the surface gliding — content jumping under a sliding window is exactly the judder. The choreography is `insertRow`'s and inherits both its traps (seed the current height before retargeting to 0; lay the collapsed START state out before animating open), plus one of its own: mark the clip `isClosing` so a re-expand landing inside the close does not have its constraint deactivated out from under it. A collapse snapshots the rows it hid and tears down only those, so a re-expand inside the same duration keeps its fresh ones. **The MODEL must move synchronously even though the teardown is deferred**: `toggleSubsection` drops the row model, reconciles the drawer and re-runs the rail extents in the same turn, because `renderedDeviceOrder()` feeds the structural-change compare and the drawer reconcile — and a deferred teardown under the instant path (bullet below) would strand the rows forever.
- **A collapsed SUBSECTION cuts the rail exactly as a collapsed CARD does** (live bug, 2026-08-11). The rail's channel still runs to the band's LAST device — `updateRailRows` indexes the FULL `deviceSections()` order, never `renderedDeviceOrder()` — and when a collapse has hidden that device the rail is CUT at THAT subsection's header with the terminus dot. Indexing the rendered order instead silently shortened the rail to a higher visible row with no dot, and, when every device sat inside the collapsed subsection, left no terminus at all: the rail rendered as a hook curling off Main Audio and ending in mid-air. The host names the cutting subsection to `setRailRows`, which points `BusRailOverlayView.deviceSection` at that subsection's own `RailSectionProviding` adapter (its header + body clip) instead of the card's — so the mid-collapse squeeze rides the clip's live height for free. **TRAP: `deviceSection` is `weak`** — the adapter is stored in `subsectionBodies` or it deallocates the instant it is assigned and the cut silently reverts to the card. The adapter also DEFERS to the enclosing card while the CARD is the collapsed one, because a card collapse never re-runs these extents and the subsection's own header has gone off screen with it.
- **Two DISPLAY-only filters sit between the device snapshot and the rows: subsection collapse, and the Bluetooth CONNECTED-ONLY listing (BT-LIST, replaced the per-device hide 2026-08-08).** Neither touches selection, membership or routing — the R12 spirit. macOS never forgets a pairing, so an opt-OUT (hide) list opened as a wall of dead rows; `isBluetoothRowListed(_:)` is opt-IN: `isAvailable`, OR an explicit "+"-menu connect attempt THIS session (`btConnectAttemptIDs`), OR `wantsAudio(_:)`, OR `isMainOutMember(_:)` (the group case `wantsAudio` misses). **TRAP: attempts are session-scoped, NOT `connectionState != .off`.** `.failed` is sticky and never clears for a paired device (no availability edge, no disappearance), so a state clause minted a PERMANENT row out of any failed attempt (off speaker, `.notPaired`, `.unauthorized`) — and no diagnosis panel with it (that intent is pruned for anything failing `wantsAudio`): unexplainable, undismissable. Bluetooth-scoped only: a playing device with no row means no volume, no mute, no way to stop it. ONE list expresses the result (`deviceSections()` → `renderedDeviceOrder()`), read by `rebuild()` and `update(devices:)`'s change test, which must weigh what SHOULD render, never the fleet, which reads an unlisted row as a permanent change and rebuilds on every backend event. The rail reads the SECTIONS, not the rendered order (bullet above): an UNLISTED device is not in `deviceSections()` at all, so it can never be the terminus, while one merely hidden by a subsection collapse still is; `rendersHeader(_:)` folds the always-on Bluetooth header into it. An unbuilt row takes its sync drawer (`reconcileSyncDrawer` retracts the intent, stops the align tick) and diagnosis panel with it, but the panel's INTENT survives and returns if it lists again mid-episode. The unlisted history keeps the two Connect surfaces below, both firing the membership-free reconnect a greyed row's click uses. AirPlay-fleet overflow stays out of scope — no `NSScrollView`, ever (rule below); only Bluetooth is bounded, by macOS's few simultaneous BT links.
- Two rebuild flavors, not interchangeable: `rebuildForOpen()` resets collapse defaults, discarding this open's manual toggles; plain `rebuild()` preserves them.
- No `NSScrollView` — height flows through `preferredContentSize`. The card stack MUST stay pinned top AND bottom in `PopoverPanelViewController.loadView`, or Auto Layout collapses it to zero. **Surplus shield** (Alec's call, 2026-08-06): the popover sizes a WRAPPER (`view`), and the required-`==` content chain lives in `contentContainer` hanging from its top, with only a required `<=` between the two and deliberately NO pull-tight pin. `fittingSizeSettled` measures `contentContainer`, never `view`. This shape is forced, every alternative measured: a required `==` straight to the sized view makes an over-tall popover unsatisfiable and Auto Layout deforms the CONTENT (the ballooned banner in the live report); a `<=`-only pin makes `fittingSize` return stale frame heights (it does not minimize to the floor — a collapsed card kept reporting the expanded height); and a soft `==` has no workable priority — `fittingSize` ignores it below ~500 while anything ≥251 out-prioritizes the banner label's 250 hugging and stretches the banner again. With the shield, an over-tall popover degrades to inert warm canvas below the last card, rows hold their geometry, and the rail stays anchored.
- **`insertRow`/`removeRow` own the re-fit; callers must NOT add their own `panelContentDidChangeHeight`** (live bug, 2026-08-06). `removeRow` defers its detach into an `NSAnimationContext` completion handler, so a caller-side re-fit measures a row that is still in the tree and about to leave — and nothing measures again once it does. The popover then stays taller than its content, one row's worth per removal. Because the stack is pinned top AND bottom (rule above), that surplus has to go somewhere Auto Layout isn't pinning: in practice the pinned banner, which balloons into a tall empty box and pushes every card below it down. Any future row primitive that mutates the stack republishes the size itself, from wherever the mutation actually lands.
- **An inserted row reveals DOWNWARD out of its sibling, by animating a CLIP HEIGHT — never by animating `isHidden`** (live feedback, 2026-08-08 — "it pushes the existing row up to fit the drawer"). `insertRow` wraps the row in a `RowClipView` (`CardView`'s collapsible body, per row: row top-pinned, bottom pin at `.defaultHigh`, `masksToBounds`) and animates that clip's height 0 → natural, so the row unfolds from under its sibling and pushes the rows below down. The mechanism it replaced animated `animator().isHidden`, which un-hides on the first frame — `NSStackView` then grants the row its full height in that same layout pass, so the CONTENT arrived instantly while the window was still animating its frame, violating the required `contentContainer <= view` from the WRONG side: taller-than-its-surface is the one case the surplus shield cannot absorb, and the deformation read on screen as the rows riding up to fit. Animating the clip instead makes the panel's height a genuinely interpolated quantity — and the window never animates at all: the frame is fixed, so the rows travel inside it. **The reveal's START state must be LAID OUT before the animation begins, not merely set** (live feedback, same day — "collapsing smooth, expanding abrupt"): measuring for `preferredContentSize` runs `layoutSubtreeIfNeeded`, committing every row below to its FINAL position, so pinning the clip to 0 without a second layout pass leaves the animation nothing to travel. `removeRow` is the exact mirror, and seeds the clip with its current height before retargeting to 0 for the same reason `CardView` does. **EVERY collapsible element here — inserted row, device-type subsection, card body (`CardView.setBodyCollapsed`) — shares ONE duration (`collapseRevealDuration`, 0.15s) and one curve, and animates a CLIP HEIGHT ONLY, never an alpha fade**, so an expand mirrors its collapse and the three read as one motion language (live report 2026-08-10 — the cards' own 0.2s + body fade "don't follow the same system"). Never mint a second constant to hand-sync. **A fold has ONE clock: `FoldAnimator`, and the window is LAID OUT from it, never animated alongside it.** A fold used to be two separately-clocked animations — the clip constraint under `NSAnimationContext` (easeInOut) and the window under `setFrame(_:display:animate:)` (AppKit's own resize curve) — and two curves on two clocks cannot stay in phase: the rail overlay overshot and the content shifted against the window for the whole travel (live captures 2026-08-11). Pre-measuring the window's target and publishing it inside the animation group only ever bounded that drift; it never removed it. The driver instead owns one animated value (the clip height), and per tick, in this exact order: (1) sets every active tween's `constant` DIRECTLY, (2) runs ONE layout + re-fit and publishes the panel's size — the window never moves; rows travel inside the fixed frame and the surplus shield absorbs the gap, (3) fires arrived completions. **Never `animator()`, never `NSAnimationContext`, never `allowsImplicitAnimation` in a fold path** — each puts a second clock back on the one value the driver owns. Retarget replaces the running tween on that constraint and continues from its LIVE constant (never a rest height, which momentarily makes the content taller than the window — the one violation of `contentContainer <= view` autolayout resolves by breaking a pin, read on screen as rows riding up to the window top); the replaced tween's completion never fires, so only the newest fold applies a terminal state. Companion trap that survives unchanged: **the START state is seeded and LAID OUT before the fold begins** — a fold cannot travel a distance the layout has already covered. Reduce Motion AND `HeadlessRuntime` resolve all three folds instantly and completely — the driver ticks off the main runloop, which the harness tools and `swift test` don't reliably spin, so a deferred terminal state would be stranded. The row is still forced `isHidden = false` before it is measured: a hidden arranged subview measures as zero height, and the single reused sync drawer (D2) carries whatever state its last mount left on it. That line is also what keeps Reduce Motion working — that path returns before the fold, so a row left hidden there would mount invisible for good.
- **The popover is the ONLY host of `PopoverPanelViewController`, in dev AND in the shipping `.app`.** `AIRPLAY_CONTROL_PANEL=1` (baked in by `scripts/make-app.sh`) re-homes **Groups** into `ControlPanelWindowController` and nothing else — `presentInControlPanel` is called once, with `MixerWindowController.contentController`. Don't chase a popover-surface bug (row heights, the sync drawer, card collapse) into the panel shell's window geometry; `NSPopover` keeps its own top edge pinned to the status item and grows downward on its own.
- `ConnectionDiagnosisView` never touches `NSPasteboard`; the host writes on `onCopyDetails`.
- `selectedAppBundleID` is host-owned, transient. All three removal entry points (± footer, "Remove from list", Delete/Backspace) must funnel through `removeApp(bundleID:)`.
- **Every card's add/remove control is the SAME primitive: `CardFooterView`, a leading-aligned ± `NSSegmentedControl` in a bottom strip** — the macOS list-management shape, never a full-width labelled button and never inline with the column titles. Applications takes both segments; OUTPUT DEVICES takes `showsRemove: false` (nothing removes a device from a list it earns by existing). The Devices "+" MOVED out of the card header into that strip (Alec's call, 2026-08-08 — a control that acts on the list belongs under the list); its card therefore has NO `HeaderAccessory` and no enabled-state refresh, and the strip is added after ALL subsections, so it is the card's last row. A sync drawer opens via `insertRow` under its own device row and can never land below it.
- **Chrome never outranks content in the card stack** (density pass, 2026-08-12). ONE hierarchy in three steps, set by weight and case rather than by which section a label belongs to: device/app NAMES are the brightest text on the panel (`Tokens.Color.label`) → a card's ENTIRE header line is one quiet legend voice (`makeLegendLabel` — small tracked uppercase at `secondaryLabel`, semibold for the section title, medium for its column titles) → subsection grouping labels a step under that. The section title used to be 14 pt at full `label`, i.e. the panel's loudest type spent on the words nobody opens the mixer to read; the hairline divider and the chevron are what separate sections, so the type doesn't have to. Two standing consequences. **No card prints a title over the SLIDER column** — a fader with a live `%` beside it names itself, and "VOLUME" was printed three times over the one trailing-anchored column; `beginCard` has no parameter for one any more, so re-adding it is a deliberate act. **A column title is printed only when that column has rows under it** — the Bluetooth subsection header renders even when nothing is listed (its empty body IS the Connect affordance), which left "SYNC" naming a column that did not exist; gated on `!section.devices.isEmpty`, NOT on collapse (a collapsed subsection still has its rows, exactly as a collapsed card keeps its own column titles), and guarded by `test_syncColumnTitleShown()`. Icon-less secondary rows (placeholder lines, the Bluetooth Connect link) sit on `PopoverColumnGrid.nameColumnLeading`, never a retyped `leadingInset + iconWidth + iconToName` — that formula predates the v4 rail gutter and hung them ~24 pt left of the names they align with. A card has exactly TWO text columns: `headerTitleLeading` (section title, subsection labels, and the card NOTE, which is a subtitle to the section title) and `nameColumnLeading` (the rows). `firstElementLeading` carries chevrons and device icons, never text.
- **Engaged-control chrome is ONE neutral tone, and hue is not how it varies.** The mute pill and its glyph, the SYNC chip's engaged fill/border/label, and the row hover and selection washes all draw `Tokens.Color.engagedChrome`; only the alpha differs (hover < selection < pill fill < full for a glyph or border). Two hues are ruled out on purpose. **Not the system accent** — `Tokens.Color.accent` is `controlAccentColor`, which follows the user's macOS setting, so it painted `#007AFF` onto a panel with no cool hue anywhere else, and it themes states that are meanings. **Not gold** — gold means signal, in the mix, carrying audio, so a gold MUTE states the opposite of what mute does, and a gold hover wash claims a membership the pointer has not granted (spec §4.8: hover is neutral, "never gold, never on the node"). The one deliberate holdout is `DeviceRowView.flashLayer`, the A4 attention pulse: that IS a signal, it lasts under a second, and neutral is exactly what it must not be. A foreign-hue sweep over the checked-in snapshots is the cheap regression check — every mixer state renders zero pixels where blue leads red.
- **A dimmed label must be dimmed BY something.** `tertiaryLabel` is right for a label on a DISABLED control — the `%` readout of an unselected row's dead slider, where the contrast floor doesn't apply and the dimming IS the "you can't touch this yet" signal (`DeviceRowView.apply`). It is wrong for live state text: the card note ("Inactive — Main Audio is using 'X'") is the only thing explaining why every row went inert, so dimming the explanation of the dimming reads as broken rather than dormant, and it lands under 4.5:1 in light. Note is `secondaryLabel`; `PopoverPanelHeaderTests` pins it with that reason attached.
- **The panel is host-agnostic; the surface is its only host (U7 deleted the `NSPopover`).** A host announces itself with exactly two calls — `surfaceDidShow()` / `surfaceDidHide()` — and assigns `surfaceResizer` to hear every size publish, which `applySurfaceResize(animated:whileApplying:)` runs; the surface uses it only to notice content taller than its fixed frame (logged once per open), never to resize; a `nil` resizer means no host is listening (pre-claim / headless). **The one visibility answer is `isEffectivelyShown`** (the host's flag, or `test_isShownOverride` headlessly) — never invent a second visibility source.
- **The surface CLAIMS the panel through `claimPanelForSurfaceHosting()` — the one handover door.** Every open of the Mixer screen must run the open ritual — `rebuildForOpen()` then the exact-fit republish — because hidden-means-idle (below) leaves everything stale on purpose.
- **The one-surface contract (`AppSurfaceController`, U3):** one shell, three lazily-built screens, EVERY swap through the shell's `setContent` (assigning `contentViewController` directly snaps the window to a 500×500 fallback — R3). ONE frame for every screen: `SurfaceLayout.width` wide, height measured on each fresh show from the Mixer's exact fit (`rebuildForOpen()` then `fittingSizeSettled()`, which already includes the chrome inset) floored at `minimumContentSize` and capped to the screen, re-asserted instantly after every `setContent` and on a pin flip, never animated, never re-centred after open. The Mixer decides the height even when Groups or Settings is the screen that opens; folds, drawers and Settings section switches move content inside the frame. Content taller than the frame is roadmap 039's call — it logs `Telemetry` `.surface`/`mixer_content_taller_than_frame` rather than clipping silently. The Groups split's fitting width is derived from `SurfaceLayout` so it can never ask for more than the frame. Leaving the Mixer screen is a `surfaceDidHide()` (metering off, transient selection dropped); entering it is `rebuildForOpen()` + `surfaceDidShow()`. Pin drives the shell's U1 manner flip and persists in `AppSettings.surfacePinned`. Every screen's content is seated below the toolbar strip — BOTH profiles now, the strip overlaps `.fullSizeContentView` content — by a MEASURED chrome inset. Two probed traps in that measure: it is the gap above `contentLayoutRect.maxY`, never the height difference (mid-resize the rect's size lags the just-set frame), and the getter must NOT force window layout (a `layoutIfNeeded()` there let a freshly mounted split view widen the window to its own minimum).
- **The launch splash is ORNAMENT, and it is gated three ways** (`SurfaceSplashView`). A menu-bar app has no launch window, so the first surface open of a PROCESS is the one moment the app can state its name — and it is the only one: never per open, never per screen. It is skipped entirely under Reduce Motion (a hold whose whole job is to be looked at is what that setting turns off) and in every `HeadlessRuntime` run, which is what keeps the snapshot tools rendering the screen they were pointed at rather than a curtain — the `window-snapshot` goldens go through this exact `show(anchorRect:)`. It leaves on whichever comes LAST of the hold elapsing and the host reporting content in place, with a ceiling timer as the backstop, because a content signal that never arrives must not leave the surface behind it; a click anywhere takes it away at once. The presentation seams (`test_headlessOverride`, `test_reduceMotionOverride`) decide whether a run DESERVES ornament, but the fade's own instant-terminal-state branch reads the real `HeadlessRuntime.isActive` — a fade with no run loop to carry it would strand the view on screen forever. **The whole first-open reveal is DEFERRED until discovery settles** (Alec's call: "splash solid, then cross-fade onto an already-settled list"): on the splash path `AppSurfaceController.show` does NOT front the window — it mounts the screen, arms `DiscoverySettleTracker` on the raw device stream, and waits; when the fleet quiets (or `ceilingDuration` backstops a network that never does), it measures the settled size, sizes the still-off-screen window to it, fronts it ONCE, and only then lays this hold over the already-settled content. The user's first sight of the surface is the settled frame — nothing slides, because there is no on-screen window to slide while the fleet streams in. This is the ONLY reliable cure for the open jump: a menu-bar-anchored window grows DOWNWARD, which no internal cover can hide, and AppKit resizes the shell window to the content controller's `preferredContentSize` DEFERRED (a synchronous `setFrame` is overridden a runloop later — verified live), so the window cannot be "held" at a wrong size while on screen; it can only be fronted already-correct. `revealFirstOpen` pins `preferredContentSize` to the floored session size as its LAST write before fronting, so a small fleet (fit below the 600 floor) does not shrink the window under the splash the instant it appears. The gating exists ONLY on the splash path, so the headless / Reduce-Motion open stays synchronous and the `window-snapshot` goldens are untouched. NOTE (pre-existing, roadmap 039): the Mixer panel IS the shell window's `contentViewController`, so while the surface is OPEN a content change that crosses the session frame — a speaker appearing/leaving, a drawer — still resizes the window on screen; only headless (no window server) is that resize absent, which is why `foldsNeverMoveTheFrame` and kin read green without proving it live.
- **Nothing in the surface is user-resizable.** `shell.setUserResizable(false)` runs once at construction; there is no per-screen drag memory. A resize affordance would fight the fixed frame — the owner ruled any width change on a screen switch "reads as the surface twitching".
- **The header is a real window-attached `NSToolbar` (`SurfaceToolbarController`), owner decision 2026-08-07 — this SUPERSEDES the custom `PopoverHeaderView` strip, its hand-drawn capsules, and the three-tier glass/frost/opaque machinery (all deleted).** `.unified` style, `titleVisibility` hidden in both profiles: the toolbar IS the one header strip — tabs as an `NSToolbarItemGroup` (`selectionMode = .selectOne`, the system draws the selection), "Audiout" as a centered label item, Pin + Quit trailing. **TRAP: the display mode must stay `.iconOnly`** (live review 2026-08-11) — under any label-showing mode macOS 26+ builds the group's picker WITHOUT its interactive expanded view, and the strip becomes an empty capsule with the tab names loose beside it and all three segments dead (Pin/Quit, plain items, still work). Tooltips, the subitems' `label`s and ⌘1/⌘2/⌘3 carry the names instead; `SurfaceToolbarTests` guards the picker's expanded view. The system owns materials and Reduce Transparency now — no tier seams exist. Tab selection stays HOST-CONFIRMED: a tap only reports through `onSelectScreen`, and the group re-asserts the host-confirmed `selectedScreen` after the callback. ⌘1/⌘2/⌘3 ride the shell panel's `keyEquivalentHandler` seam (a toolbar item group carries no per-segment key equivalents). One toolbar per process — it belongs to the WINDOW, so there are no sibling headers to sync. The toolbar lives in this target, not the shell: it names the three screens, and the shell stays content-agnostic.
- **Hidden means idle, deliberately** (audit B8): `update(devices:)`, `applyRoutedAppRunning`, `setLocalFallbackActive`, `applyNoteSlot` and both level pushes all skip their work behind `isEffectivelyShown`. Nothing is lost — every open runs `rebuildForOpen()` over the state ingested meanwhile — whereas rebuilding anyway turned each backend event into a full hidden rebuild, which stormed under volume-key repeat. Don't "simplify" one of these gates away.
- `surfaceDidHide()` also drops what must not outlive a session: the transient app-row selection, and every meter's last reading (`resetLevel()` on `deviceRowsByID`, `mainOutRow` and `appRowsByBundleID`) so a reopen never shows a stale bar. Both calls drive `(backend as? MeteringControlling)?.setMeteringActive(_:)` via `onMeteringActiveChange`, so the backend pays for RMS (and the metering-only taps) only while a UI exists to show it to.
- `PopoverController.updateLevel(_ rms:, for id:)` is the live push path from `AppDelegate`'s `.level` handling; `test_pushLevel(_:for:)` is the same dispatch with NO visibility gate, for headless snapshots/tests. Both route to `deviceRowsByID[id]?.setLevel(rms)` and, for the Main Out id, `mainOutRow.setLevel(rms)`. `updateAppLevel(_:for:)` mirrors it for the Applications card (gate-free twin `test_pushAppLevel(_:for:)`, routing to `appRowsByBundleID[bundleID]?.setLevel(rms)`) — but an app level never feeds `mainOutRow`, which mirrors the selected DEVICE's level, not any one app's contribution. `makeAppRow` constructs its `AppRowView(showsMeter: true)` so the row actually has a meter to push into.
- **Energize (item 9)** is orchestrated here, drawing-only. `mainOutRow(_:didSelect:)` (the source-switch delegate) calls `beginEnergize(to:)` before `rebuild()`: it posts the VoiceOver transition announcement (always — the announcement is independent of Reduce Motion) and, unless Reduce Motion is on, seeds `energizePendingIDs` with the SELECTED members still `.off` — the rows the left rail already runs through, so the clean cases (switch to Selected Devices / a derived-identity group) light their spine while a genuinely-diverging group target stays dormant (§4.7). `refreshDeviceRows()` calls `reconcileEnergize()` first: it prunes the beat off members that have left `.off` (their model node takes over) and fires the one-shot settle announcement once the target stops moving. No timers — the top-to-bottom fill rides the live `connectionState` progression (each member's own connect-brighten is the per-row `DeviceRowView` cross-fade, item 8). Hooks: `test_switchMainOut`, `test_setEnergizePending`, `test_energizePendingIDs`, `test_energizeActive`, `test_lastEnergizeAnnouncement`, `test_reduceMotionOverride`.
- **The rail connect pulse fires from `update(devices:)`'s connected-member diff, never from the overlay's draws.** `lastConnectedMemberIDs` (predicate `isMainOutMember ∧ .connected`) is the one firing baseline; it advances while the surface is hidden too, so a reopen can never fire. A genuine join reaches the overlay through `panel.playRailConnectPulse` → `BusRailOverlayView.playConnectPulse`; the overlay is render-only for the pulse, so collapse/expand/rebuild/open cannot fire it by construction, and the Groups editor host simply never calls it. An overlay SIZE change (a panel reflow) cancels an in-flight bead, so a pulse never flies a path captured against geometry that has since moved.
- **The live-removal undo is offered ONLY when the click actually silences a room, and the facts are read BEFORE the edit.** `isLiveMainAudioRemoval` = the device is an `isMainOutMember`, is `.connected`, AND the Main Audio spine is armed (`MainOutRowView`'s own `isSpineLive` recipe: a connected unmuted target, or the local-only resting case) — after `setDeviceSelected` runs, two of those three have already changed, so the read cannot move. An idle removal gets nothing: no pill, no timer, no announcement. The offer is keyed by device id on the CONTROLLER, never on the row: the toggle repaints (sometimes rebuilds) the whole card, so row-owned state would be destroyed by the click that raised it — and id-keying is also what expires it for free when a row is rebuilt for another device or the device re-joins the mix (`applySelectionState` withdraws it on `selected`). It never outlives the surface (`surfaceDidHide`). Its announcement shares the energize channel (`postAnnouncement`) — one Main-Audio spoken channel, one test seam.
