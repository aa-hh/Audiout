# AudiouterSharedUI

## Purpose

AppKit row views shared by the popover (`AudiouterPopoverUI`) and the Groups screen (`AudiouterWindowUI`) so both hosts render the same device row from one implementation. Views here are pure UI: controls route out through a per-view `Delegate` (or closure), never touching a backend, store, or `GroupController` directly. For the routing model these rows render, see [../../AGENTS.md](../../AGENTS.md).

SharedUI also now hosts shared WINDOW CHROME, not only row views: `ControlPanelWindowController` is the sticky floating-panel shell that IS the one surface's window (the `AIRPLAY_CONTROL_PANEL` opt-in flag is retired — the shell always ships; `AppSurfaceController` in `AudiouterPopoverUI` owns it and swaps the Mixer/Groups/Settings screens through it). It stays content-agnostic: one panel, content swapped via `setContent(_:)`; it knows nothing about groups, devices, or settings — callers own their own content `NSViewController` and push it in. T11 gave it a custom-drawn arrow "beak" tying it to the menu-bar status item, right-edge alignment, and an open/close fade — see the exception rule and `ControlPanelBackingView` below.

## Rules

- Views never read shared model state — hosts push a plain-value snapshot via `apply(...)`. `DeviceRowView` takes `selected` explicitly (membership lives in `GroupController`, not `Device`); `AppRowView` takes an isolated `Configuration`.
- Row geometry lives in `PopoverColumnGrid` (named constants, no magic numbers) — columns anchor to the row's *trailing* edge, so slider/status/trailing-control columns line up across sections despite different leading controls.
- Hover state is transient, separate from selection, reconciled via an app-local `.mouseMoved` monitor cleared on every `apply` — an `NSTrackingArea` alone never fires `mouseExited` for a bottom-most row with an untracked dead-zone below it.
- `DeviceRowView` computes `isInMenu` live from `enclosingMenuItem` to pick its drawing path and accessibility role — don't hardcode one path for both hosts.
- `DeviceRowView.draw(_:)` and `AppRowView.draw(_:)` are drawing-only row backgrounds: stack-hosted rows (popover card / mixer window) get no system row chrome, so each paints its own inset rounded selection/hover pill (unified `PopoverColumnGrid` alphas), and a menu-hosted `DeviceRowView` must paint the menu highlight itself — AppKit draws no background behind a custom menu-item view.
- Each view exposes `test_*` hooks (`test_setVolume`, `test_toggleEnabled`, …) that must drive the exact same delegate path as the live control, since gestures can't be synthesized headlessly.
- The device row's trailing control is an `NSButton` checkbox under a "Selected" header (membership in "Selected Devices"), not an `NSSwitch`; the column is not "Enabled".
- `DeviceRowView.apply` takes `controllable` separate from `selected`: slider/mute enablement follows `controllable`, but the checkbox and the sublabel's "System" token follow `selected` alone.
- **The membership checkbox's ENABLEMENT is intent-derived: `isAvailable || selected`** (live bug, 2026-08-06). The native backend's failure paths pair `.failed` with `isAvailable = false` while the user's selection intent stays true, and every deselect affordance (checkbox hit-test, name click, node click, keyboard/VoiceOver) funnels through this one flag — availability-only gating made a stuck-`.failed` row physically un-deselectable. A SELECTED row therefore always keeps a live toggle; an unavailable+unselected row keeps the dead one. Slider/mute stay availability-gated ("not adjustable right now") — only the intent control is exempt.
- The popover header's icon buttons are stock `NSButton` (`bezelStyle = .accessoryBar` with `showsBorderOnlyWhileMouseInside = true`) — no custom hover-button class exists here.
- `DeviceRowView` gets a `showsMeter: Bool = false` init param; the mixer window and `GroupRowView` never pass `true`, so they stay visually unchanged. The Warm-Signal-v4 meter (`LevelMeterView`) lives UNDER THE NAME inside a vertical `identityStack` (row order name / meter / sublabel), shown (un-hidden) only on armed rows — the stack recentres its visible lines, so no manual name-offset juggling. `setLevel(_:)`/`resetLevel()` are no-ops when `showsMeter` is false; `test_meterLevel()` returns the last pushed level (`0` with no meter or after a reset).
- `LevelMeterView` is layer-backed, non-interactive (`hitTest` returns `nil`). It is a SHORT HORIZONTAL bar (`PopoverColumnGrid.meterUnderNameWidth × meterUnderNameHeight`, v4 §Call-1) whose fill WIDTH tracks the level, growing left→right. Its fill is the Warm Signal **position-fixed warm gradient** `ember → gold → caution` (spec §1/§3.3): a full-width `CAGradientLayer` revealed through a leading-anchored mask, so hues live at fixed track widths and only the mask width moves per frame. `caution` is the ceiling — **failure red never appears in a meter** (house rule 8). It exposes `setLevel(_ rms: Float)`, `reset()`, `static let columnWidth: CGFloat` (now the bar THICKNESS), and deterministic hooks `test_setDisplayedLevel(_:)` / `test_targetLevel` / `test_displayedLevel` / `test_gradientColors` (no display link). Ballistics (attack faster than decay) live in the pure `static func ballisticsStep(displayed:target:) -> CGFloat`; a zero-target-at-rest `setLevel` no-ops instead of spinning up a display link (energy rule).
- The **gold route-armed corner dot** (`RouteArmedDotView`, spec §3.3, S2) sits on the icon's bottom-right corner (the retired connection dot's `statusDotInset` position) in `DeviceRowView` AND `MainOutRowView`. It is PURE MODEL STATE, never RMS (R3): the row computes `routeArmed = (inActiveTarget ∧ connected ∧ !rowMuted ∧ !masterMuted) ∨ liveAppNames≠∅` in `apply` — the host passes `masterMuted:` and `inActiveTarget:` (membership vs the ACTIVE Main Out target; `nil` falls back to `selected`). Armed = `gold` disc + static `glow` halo; unarmed = the dark `dotSocket`. The arm transition blooms `ember → gold` (≤450 ms ease-out) only on a false→true transition after the first apply, on screen, Reduce Motion off — model layer stays settled, so `cacheDisplay` snapshots are deterministic. Hooks: `test_routeArmed`, `test_dotFillColor`, `test_dotHasGlow`, `test_dotIsBlooming`.
- **Mute channel** (S3, spec §3.4/§3.5): a muted row's mute button draws a filled accent PILL on the real `NSButton`'s backing layer (glyph NEVER swaps to a slash — locked decision; behavior/keyboard/VoiceOver untouched); its meter DRAINS via the existing decay ballistics (`setLevel(0)`, never a new animation; pushes while muted are coerced to 0); its dot goes dark (the predicate's unmuted term); and its sublabel gains a leading small-caps `MUTED ·` token (micro-label voice, `Tokens.Font.microLabel`) **only when a feed sublabel already exists** — never a standalone line, so row height never changes (R7). Master mute drains/darkens without the per-row token (the Main Out pill carries it). Row/Main-Out `accessibilityValue` composes `"muted"` / `"armed"` / `"playing here"` as the spoken equivalents.
- **Collapse-reactive rail** (2026-07-22): `BusRailOverlayView` is fed the two collapsible cards the rail spans via `RailSectionProviding` (the `originSection` holding Main Audio, the `deviceSection` holding the device rows; `CardView` conforms). It reads their LIVE body-clip frame + header every draw and resolves the drawn shape through the PURE `RailPlan.resolve` (all geometry pre-converted to overlay space, so it is deterministic and unit-testable at any intermediate clip height — `BusRailCollapseResolveTests`). Four behaviors: (1) a collapsed device section CUTS the rail with a small gutter terminus dot (`railCollapsedTerminusDotDiameter`) at its header instead of drawing now-hidden nodes; (2) collapsing the ORIGIN section moves the origin UP from the Main Audio ring to that section's header dot — keyed off the ring falling outside the section's live clip band, not the collapse flag, so it rides up rather than snapping; (3) the terminus/origin track the shrinking clip floor FRAME-BY-FRAME (the in-sync squeeze) — the host's CARD STACK (`RailStackView.layout`) re-invalidates the overlay on every collapse-animation layout pass, so no new timer is needed. **The invalidation must hang off a view that re-lays out when the ROWS move, not off the top-level container** (live bug, 2026-08-06): a container's `layout()` does not run when only its descendants re-lay out inside an unchanged frame, so hooking it there left the overlay compositing its last painted figure over rows that had since moved — the whole rail displaced by a rigid offset. Never dirty the overlay from an ancestor's `viewWillDraw()` either: that schedules a display pass on every display pass, forever; (4) `resolve` carries no state, so re-expanding restores the exact prior rail. The all-EXPANDED render is byte-identical to before (the device clip floor sits below every node → no cut), so the checked-in `popover-snapshots/*.png` are unchanged. Reduce Motion is honored by the existing non-animated collapse path (`setCardCollapsed`) resolving both end states synchronously.
- Warm-Signal-v4 §Call-1 re-homes the leading gutter from a meter column to the **membership rail's LEFT SPINE**. `firstElementLeading(indented:)` reserves that gutter as `(indented ? indentedLeadingInset : leadingInset) + busGutterWidth`, where `busGutterWidth` is DERIVED from the rail geometry (`railGutterCenterX + busNodeDiameter/2 + busNodeClearance − leadingInset`) — so widening `railGutterCenterX` / `busNodeClearance` (Alec's node-clearance refinement) reflows only the LEADING columns; VOLUME/OUTPUT are trailing-anchored and hold. The under-name meter is sized by `meterUnderNameWidth`/`meterUnderNameHeight`.
- `AppRowView` gets the same `showsMeter` init param and the same under-name `LevelMeterView` inside an `identityStack` as `DeviceRowView` (v4 §Call-1); the icon leads at `firstElementLeading(indented:)`, so app icons align with device icons. App rows carry NO bus node — the left gutter is reserved but empty, mirroring how device rows leave the trailing dropdown column empty. `setLevel(_:)`/`resetLevel()`/`test_meterLevel()` mirror `DeviceRowView`'s signatures; the per-app level signal (`BackendEvent.appLevel`) drives `setLevel(_:)` via `PopoverController.updateAppLevel`, never from `apply(_:)`.
- **Bluetooth rows' SYNC control carves the trailing slot, never the grid.** A `showsSyncControls` row keeps the slider/`%` columns at their exact shared anchors; the SYNC control occupies the trailing slot's LEFT portion and the FEED pill right-aligns into `btFeedReserveWidth` (locked spec: feed pill far right — BT rows are never per-app route targets, so one pill is the ceiling). Since PLAN-BT-SYNC-DRAWER T6 that control is ONE read-only value chip (`syncChipButton` + the drawing-only `SyncChipCell`) that reports `didToggleSyncDrawerFor` and nothing else — it never edits or clamps a trim. Every editing behaviour (steppers, typed value, the `metronome.fill` align toggle — D9) lives in `BTSyncDrawerView`, so the row can never hold a second, divergent copy of the rules. Three chip states: tuned ("22.4 ms", solid `hairline` outline), UNTUNED ("Not set" in `tertiaryLabel` inside a DASHED outline — D10's discoverability affordance, since zero reads as finished), and drawer-open (the mute pill's engaged recipe: translucent `accent` fill at `mutePillFillAlpha` + accent glyph — never a solid `gold` fill; gold is the route-armed vocabulary). Trim range/step live in `AudiouterCore.BTSyncTrim` — one clamp shared with the backend; the geometry is the `sync*`/`btFeed*` constants in `PopoverColumnGrid` (the Figma contract mirrors that file), and the subsection header's SYNC title centres on the derived `syncCenterFromTrailing`, so re-sizing `syncChipWidth` re-centres the title in lockstep. A DISCONNECTED row shows the saved value on a DEAD chip (nothing to tune while the speaker is away). TRAP: the failed FEED pill renders `ConnectionFailure.headline`, not a hardcoded "Couldn't connect" — `.connectedElsewhere`/`.notPaired` must read distinctly; only the non-bus legacy sublabel keeps the generic string.
- **A greyed BLUETOOTH row's name click CONNECTS, never selects** (`deviceRowDidRequestReconnect`, BT-UI "click to connect" is the row's ordinary click behavior): ordered BEFORE the checkbox-enabled guard because an unavailable+unselected row's checkbox is disabled — that disabled state IS the greyed case. A BT reconnect also pairs `.connecting` with `isAvailable == false` (the endpoint only appears on success), so `updateBus`/`updateFeedText` carry BT-scoped branches that show the connecting node and suppress the "Unavailable" pill while the attempt is in flight — don't "simplify" the availability arm back over them.
- **Instruments reconcile accessibility-display changes LIVE**: `HaloRingView`, `RouteArmedDotView`, `WarmCanvasView`, `LevelMeterView`, and `DeviceRowView` itself (the item-8 connect-edge brighten) observe `NSWorkspace.accessibilityDisplayOptionsDidChangeNotification` (workspace notification center, selector-based) because a mid-session Reduce Motion / Increase Contrast / Reduce Transparency toggle arrives NEITHER through `apply` nor (for Reduce Transparency) through `viewDidChangeEffectiveAppearance` — a new animated/token-colored instrument must do the same or it silently ignores the toggle until the next model push. Reduce-Motion reads go through a `test_reduceMotionOverride` seam (`nil` = live value) so headless tests can drive both sides of the toggle by posting the real notification.
- **The accent dial is a THIRD live re-resolution trigger, and a layer-color instrument must observe it.** `Tokens.accentStyleDidChangeNotification` is posted from the dial property's own `didSet`, so no call site can move the dial silently. A `draw(_:)` instrument needs only an invalidation (it re-reads its tokens every pass); an instrument that stamps a resolved `CGColor` onto a `CALayer` keeps showing the old accent until something re-stamps it — `viewDidChangeEffectiveAppearance` and the a11y notification do not fire for an app-internal setting. That was a live bug: the Main Audio ring kept its gold while the rail it joins had already re-tinted.
- **The rail's hook, its `.member` segments, and the Main Audio ring are ONE line, enforced by construction, not convention.** All three take their tone from `Tokens.Color.spineTone(armed:)` — `BusRailOverlayView` at draw time (the hook AND every member segment read the SAME resolved `originColor`, so the corner and the line leaving it can never step), `HaloRingView` at stamp time — and `HaloRingView` stores the armed STATE (`connectedSpineArmed`), never a resolved color, so a host cannot hand it a tone the rail didn't choose. Two call sites each naming `gold`/`ember` is what let the dial move one and not the other. SCOPE: this pair only. The device rows' ring stays the hue-neutral `ringConnected`, which the dial never remaps and the a11y plan still owns as an authored hex — do not pull it onto the dial. `RingRailToneLockTests` sweeps every dial position × appearance × armed/ember against the rail's real drawn pixels.
- **TRAP: `CALayer.add(_:forKey:)` ignores a custom key for a `CATransition`.** Unlike `CABasicAnimation` (`RouteArmedDotView`'s bloom), a `CATransition` is always filed under the literal reserved string `"transition"` regardless of what you pass as `forKey` — verified empirically, not documented behavior most people expect. `DeviceRowView`'s connect-edge brighten (item 8) uses a `CATransition` for a whole-subtree cross-fade and has to look it up/cancel it by that reserved key, not a project-specific one; a future cross-fade (e.g. T9's energize sweep) hits the same trap.
- **Energize pending beat** (spec item 9, the source-switch "press-play"): `DeviceRowView.apply(energizePending:)` is a DRAWING-ONLY input the host raises on the members of a Main-Audio source switch that haven't started connecting yet — while the device is still `.off` it renders `MembershipBusView.Node.pending` (ember dashed, ON the spine) instead of its resolved node, giving the instant drop-to-pending BEFORE the backend reports `.connecting`. It NEVER touches the model: the `.off` guard in `updateBus()` means the moment `connectionState` advances the model node (`.connecting` → `.member`) supersedes the beat, so the host can leave the flag raised and the node hands off cleanly. Gated on `reduceMotion` (the beat IS the sweep — Reduce Motion removes it, snapping to the resolved node), and `accessibilityDisplayOptionsDidChange` re-runs `updateBus()` so a mid-flight toggle drops it live. Its VoiceOver equivalent: a pending `.off` row speaks "connecting" via `accessibilityStateSuffix`. `BusRailOverlayView` colours the segment above each stop in the spine tone for a `.member` (gold on a live spine, ember on a dormant one), ember for pending/connecting, and DIM (`tertiaryLabel`) for a `.failed` in-spine node (item 9 "failed segment dim") or a dormant-divergent stop. Hook: `test_energizePending`.
- **Warm fader skin** (spec §5 "slider track/knob look"): the row volume sliders (`DeviceRowView`, `MainOutRowView`, `AppRowView`) wear `WarmFaderCell` — a drawing-only `NSSliderCell` subclass overriding ONLY `drawBar`/`drawKnob` (tracking, keyboard, scroll-wheel, `isContinuous`, VoiceOver, focus ring all stock; the cell swap happens FIRST in `buildSubviews` so the min/max/target/action config after it lands on the new cell). It draws the flat recessed `well` trough (`faderTrackHeight` ≈ 5 pt, `faderRim` rim + drawn inner top shade — no layers), the gold gradient fill (dim end = `ember` pre-blended halfway toward `gold` so the low-value end clears the trough) ONLY while route-armed ∧ enabled — the EXACT §3.3 predicate the row's `RouteArmedDotView` renders (one armed truth, two instruments; `AppRowView` hosts no dot and uses its spec-§5.1 routed ∧ running equivalent) — a hue-neutral `ringConnected` fill otherwise (dimmed to `faderDisabledAlpha` when disabled), and a rounded-rect `faderThumb` thumb (≈10×17 pt, ≥3:1 vs canvas AND trough in both themes — measured ratios on the token; derived darkened outline, 1 px top highlight). All colors resolve through `Tokens` at draw time, so light/dark, Increase Contrast, and the accent dial (under `.systemAccent` the engaged fill becomes `controlAccentColor` + its ×0.55 companion) land for free; drawing is steady-state and byte-deterministic under `cacheDisplay`. Hooks: per-row `test_isFaderEngaged` / `test_hasWarmFaderSkin`, plus `DeviceRowView.test_fireSliderAction(settingValueTo:)` (real AppKit target/action dispatch, not the delegate shortcut) and `test_sliderConfiguration`. `GroupRowView`'s master slider and Settings' connect-volume slider deliberately stay stock.
- The device row's VoiceOver contract is ONE composed announcement: label = identity + membership + volume + connection clause, value = the live-signal words (`muted` / `armed` / `playing here`), hint = the blocked-row refusal reason — each channel spoken exactly ONCE, never duplicated across label/value, and the membership clause uses the BUS vocabulary ("in main audio") on `showsBus` rows so it matches the checkbox's own label.
- Known stability findings in this target carry `STABILITY(id)` inline markers — details and fix sketches in [../../../dev/notes/stability-audit-2026-07-18.md](../../../dev/notes/stability-audit-2026-07-18.md).
- `DeviceIcon` is the single resolution point for "what SF Symbol represents this device/group" — `DeviceIcon.resolve(_:default:)` falls back to the kind/group default when an override is `nil` or no longer resolves on this OS (`DeviceIcon.isValid`), so every row/detail/icon-well caller shares one staleness check instead of its own nil-check-plus-validate dance. `DeviceIconController` is the only place a per-device icon override is looked up or written (`AudiouterCore.DeviceIconStore` persists it); only the bare symbol name string is ever persisted, never a resolved image or a color.
- **`WarmNameFieldCell` is the inline-rename skin** (Groups window header, design review 2026-07-25): a DRAWING-ONLY `NSTextFieldCell` subclass — the same "only the drawing changes" contract as `WarmFaderCell` over the sliders and `InvisibleSwitchCell` under the membership node. The host swaps the cell in FIRST and configures the field after, so first responder, the field editor, Return/Escape, selection and VoiceOver stay stock `NSTextField`. It paints a `Tokens.Color.raised` fill (pairing with the `DeviceIconWellView` beside it), a 1pt `Tokens.Color.hairline` border at `PopoverColumnGrid.titleFieldCornerRadius` (NOT a capsule — that shape belongs to the engaged mute pill), the shared neutral hover wash (`rowHoverWashAlpha`, byte-identical to the icon well's highlighted state), and a trailing `pencil` SF Symbol tinted `Tokens.Color.secondaryLabel` at `PopoverColumnGrid.editAffordanceRestAlpha`/`editAffordanceHoverAlpha` — HIDDEN while the field is being edited, since the caret carries that meaning and the glyph collides with it at the end of a long name. Text insets (`textInsetLeading`/`textInsetTrailing`) go through `drawingRect(forBounds:)` ALONE: that is the single seam AppKit routes both the drawn string and the field editor's frame through, so also overriding `select`/`edit` would inset a second time. It sets NO text colour — the Groups window's text is frozen to stock AppKit semantics. `drawFocusRingMask(withFrame:in:)` traces the box so AppKit's own ring hugs the visible field.
- **`InvisibleSwitchCell` is now shared, not duplicated.** The membership checklist in the Groups window reuses the same `InvisibleSwitchCell` implementation (`public` visibility) that `DeviceRowView` introduced for the popover — one implementation for the "invisible checkbox + gold node" pair, now serving both hosts.
- **`SidebarWarmSurfaceView` is a second approved custom-drawn element** (alongside the icon-well edit badge), confined to `SidebarViewController.swift` — a non-interactive warm-tinted overlay sitting between the sidebar's system material (`NSVisualEffectView`) and the outline view on macOS 26+. On older systems — and on 26+ while Reduce Transparency is on (re-read per repaint, seam `test_reduceTransparencyOverride`) — it renders an opaque warm fallback. The injectable seam `SidebarViewController.osSupportsLiquidGlassSidebar` gates the OS branch.
- **`Tokens.Color.well` and `.hairline` are now actively used.** Previously unused tokens now serve the Groups window: `.well` fills every `GroupedSectionView` (the editor's header + membership list, the detail pane's header + metadata sections) and `.hairline` draws both their borders and the inset dividers between rows. `.raised` fills the CONTROLS that sit on those sections — the icon well and the rename field — so the pair carries its own measured floor (`MembershipWellContrastTests`: raised vs well 1.186:1 dark / 1.251:1 light).
- **`ControlPanelBackingView` is an APPROVED custom-drawn exception (T11)** to the "stock components only" house rule (root `AGENTS.md`), the same category as `AudiouterWindowUI`'s icon-well hover scrim: NSPanel has no built-in arrow/notch, so tying the control-panel shell visually to the menu-bar status item requires custom drawing. All of it is confined to this one view — nothing else in the shell hand-draws chrome.
  - **Two-window shell, not one.** The real content panel (`ControlPanelWindowController`'s `window`) keeps its `.titled`/`.closable` style mask bits UNCHANGED from T1 — `performClose(_:)` silently no-ops (no `windowWillClose`, no `onClose`) on a window whose style mask lacks `.titled`, verified empirically, and that timing is load-bearing for the "land home" contract and this file's own tests. Instead the panel is made VISUALLY borderless (transparent title bar + hidden title, `isOpaque = false`, no shadow of its own, `isMovable = false`); the standard buttons are ALL hidden unpinned (owner decision 2026-08-07 — Escape and the menu-bar toggle close the bubble), and miniaturize/zoom stay hidden in both profiles (neither is in the style mask, so both would be dead chrome). Those manner bits are PROFILE-dependent — see the two-profile bullet below. Escape closes too, wired deterministically via `ControlPanelPanel.cancelOperation(_:)` → `performClose(_:)` rather than incidental default behavior. A second, purely decorative `NSWindow` (`backingWindow`, borderless, `ignoresMouseEvents = true`, attached via `addChildWindow(_:ordered: .below)`) sits behind it hosting `ControlPanelBackingView`, which draws the rounded bubble + beak and owns the shape-fitted shadow (`hasShadow = true` + `invalidateShadow()`). Because the decorative window ignores all mouse events, hosted content in the real panel is never shadowed by it — this is the "correct hit-testing" guarantee, not a hand-rolled hit-test dance in the content's own view tree.
  - **Two manner profiles, one window (`setPinned(_:)`).** UNPINNED is the transient anchored bubble; PINNED is an ordinary window (movable, `hidesOnDeactivate` off, normal level, the standard close button shown, beak detached, frame autosave armed via the restore-then-arm order: `setFrameUsingName` first — its Bool is the only trustworthy "was a frame restored" signal; `setFrameAutosaveName` afterward only arms ongoing saves). **`titleVisibility` stays `.hidden` in BOTH profiles** (owner decision 2026-08-07: no separate title bar ever — the surface's window-attached toolbar is the one header strip; only `titlebarAppearsTransparent` flips, giving pinned the system strip material and unpinned a transparent strip on the bubble). **Only manner/appearance bits ever flip — never the style mask:** `.titled`/`.closable` have to survive BOTH profiles or `performClose` silently no-ops and Escape/`onClose`/"land home" die with it — never mask surgery. `isFloatingPanel` IS the level switch (it writes `level` in both directions — measured), so assigning `level` around it is dead code. Pin state is runtime-only here; persisting the user's choice belongs to the caller. Un-pinning an ON-SCREEN panel re-anchors it immediately, because it grows its beak back that instant and a beak may never point at nothing. **`.resizable` is the one style-mask bit a caller DOES flip, deliberately** — `setUserResizable(_:)` (F3) is orthogonal to `setPinned(_:)` and untouched by `applyPinProfile()`: the surface toggles it per SCREEN (exact-fit screens off, Groups on), independent of pin state, so it survives a pin flip unless the caller changes it.
  - **The shell hosts a caller-attached toolbar but attaches none itself, and `ControlPanelPanel.keyEquivalentHandler` is the caller's pre-dispatch key hook** — both exist because the surface's toolbar names screens and the shell must stay content-agnostic; an unhandled event falls through to stock dispatch.
  - **TRAP: the status-item click resigns key BEFORE the button's action runs.** An unpinned panel dismisses on click-outside (`windowDidResignKey`), so that click closes the panel and the action then sees a closed panel and reopens it — the panel could never be toggled shut from the menu bar, it would only flicker. A click handler MUST ask `consumeRecentResignDismissal(within:)` first; it consumes, so one dismissal can never swallow a second, later click. Two conditions on that dismiss are each a separate bug if dropped: a live SHEET suppresses it (dismissing the host kills the sheet mid-edit), and an APP-SWITCH resign is the `hidesOnDeactivate` tuck-away rather than a close — the discriminator is whether this app is still active.
  - **The panel's own content view controller is left completely alone** (`window.contentViewController === controller` still holds, exactly like T1) — the shell never wraps or reparents caller-owned content. The only touch is cosmetic: `setContent` gives the hosted view a layer, a corner radius matching the bubble's, and a TRANSPARENT (not opaque) background. The transparency is deliberate: the panel is transparent and the backing bubble already fills a LIVE warm `Tokens.Color.panel` — the ONE surface canvas (owner decision 2026-08-07: every screen sits on the Groups content pane's flat warm `panel`; this supersedes Warm Signal §5.4's `canvas` here AND §5.2's "Settings on stock chrome" for the in-surface world) — so bubble, beak, toolbar strip, and content read as ONE warm shape, light and dark. Content that paints its own background (the Mixer panel, Groups' content pane, Settings' root) paints that SAME `panel` fill via `WarmPanelView`, so covering the bubble changes nothing. An earlier opaque `windowBackgroundColor.cgColor` fill here was a frozen snapshot that couldn't track a theme change — that was the dark-mode "half-render" (light content pane, dark sidebar); see `configureContentAppearance`.
  - **`show(anchorRect:)` reads the panel's frame back AFTER `makeKeyAndOrderFront`, never before.** AppKit can silently re-constrain a window's position to `NSScreen.visibleFrame` the instant it's actually ordered on screen; positioning the backing window from a frame captured before that happens desyncs the beak from the panel (found by manual verification, not by the structural unit tests — they never check the backing window at all). The panel's own vertical clamp also reserves `ControlPanelBackingView.beakHeight` above itself for the same reason: without it, a panel anchored near the screen's top edge (the normal case — that's where the menu bar is) triggers exactly that silent re-constrain on the backing window alone, breaking lockstep.
  - **Open/close is a plain opacity fade**, not a slide or scale-from-anchor: a transform-based "grow from the beak" would also need to run on the HOSTED content's layer to stay in lockstep with the bubble, and that layer belongs to caller-owned content whose `isFlipped` state this shell doesn't control, so a translate could animate the wrong direction depending on it. The fade is flattened (skipped entirely) under `NSWorkspace.shared.accessibilityDisplayShouldReduceMotion`. The close side is explicitly best-effort: `onClose` must keep firing synchronously from `windowWillClose` exactly as in T1 (✕/Esc/performClose/the test suite all depend on that timing), so the real close is never deferred to let the fade finish — in a live app there's usually enough of an async handoff to the window server for it to read as a transition; in a fast/headless run it may not render at all. A fully guaranteed close transition would require deferring the real close, which was deliberately rejected rather than hacked around.
  - **`windowDidResize` keeps the decorative bubble/beak backing window in lockstep when the user drags the panel's (`.resizable`) edge.** `addChildWindow` tracks the parent's TRANSLATION automatically but never its SIZE — confirmed by a manual probe (`setContentSize` alone desyncs the child at its old size; `setFrameOrigin` alone tracks correctly) — so `show(anchorRect:)`'s end-of-show lockstep isn't enough once the panel can be resized after the fact. The delegate method re-runs that same lockstep math in the same order (resize `backingWindow` first, THEN recompute `beakFraction` off the remembered anchor, `invalidateShadow()` last) every time the panel's frame size changes. This two-window lockstep invariant has no other structural test coverage — a future change here must re-verify it by hand, the unit tests only assert what this task added.
- **`setContent`'s `defaultSize:` seeds the panel's size on the FIRST mount of a given content controller only** (tracked by `ObjectIdentifier`) — re-hosting an instance that has mounted before is a pure content swap, never a resize, so a size the user has since dragged survives a swap away and back. This is the DELIBERATE OPPOSITE of `AudiouterSettingsUI`'s "re-measure content before every show" rule (`AudiouterSettingsUI/AGENTS.md`): Settings re-measures every show because its window is otherwise fixed-size and a stale saved frame must never stick, but this shell's panel is user-resizable and the owner's call is that a size he drags should hold for the rest of the process's life (never persisted — it resets on quit, not before). The panel's `isReleasedWhenClosed = false` plus the shell being constructed exactly once per process (`AppDelegate`) is what already makes a drag survive close/reopen — `defaultSize:` only has to seed a sensible size ONCE, never re-measure. Do not "fix" this into consistency with the Settings rule; the two are opposite on purpose and re-measuring here would silently stomp the drag.
  - **TRAP, found by manual AppKit probe: reassigning `window.contentViewController` is NOT size-neutral by itself.** AppKit resizes the window to a generic `(500, 500)` fallback the instant a view controller (new OR previously hosted) is (re-)assigned, before `setContent` gets to size anything — so a naive "only call `setContentSize` on first mount" guard is defeated by the assignment alone, and a re-host would silently snap to `(500, 500)` instead of holding its current size. `setContent` has to capture the panel's size BEFORE reassigning and explicitly restore it right after on every re-host (not just skip resizing) — `defaultSize:` only ever wins on a controller's genuine first mount.
- **Always write `NSApp?.`, never bare `NSApp.`** — anywhere in the UI library targets (this one, `AudiouterPopoverUI`, `AudiouterWindowUI`, `AudiouterSettingsUI`, `AudiouterOnboardingUI`). AppKit declares the global as `NSApplication!`, so `NSApp.currentEvent` force-unwraps `NSApp` ITSELF before the `?` on `.currentEvent` applies. No test in `AudiouterCoreTests` ever starts an `NSApplication`, so `NSApp` is nil in any test process that hasn't incidentally touched `NSApplication.shared` — a bare `NSApp.` in a code path a test drives (a slider action, an appearance read) traps with "Unexpectedly found nil while implicitly unwrapping". This bites hardest under `swift test --filter` on one suite, where the incidental initialization that masks it in a full-suite run isn't there. Optional-chaining the global is free: `NSApp?.currentEvent` flattens back to `NSEvent?`, and the void calls (`NSApp?.activate`, `NSApp?.terminate`) simply no-op headless. `AudiouterApp` (the executable) is exempt — it is not in a test target and `NSApp` is always live there.
