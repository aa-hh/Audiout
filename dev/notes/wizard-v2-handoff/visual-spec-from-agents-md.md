# Wizard visual/design spec (extracted from AudioutPopoverUI/AGENTS.md)

Extracted verbatim during the AGENTS.md cleanup pass, from the bullets covering the
BT alignment wizard sheet (formerly lines 45-46 of
`AudioutCore/Sources/AudioutPopoverUI/AGENTS.md`). This is a design record of
visual/copy decisions — pixel radii, wobble amounts, plate ink, title/keycap
centering math, stage height derivation, spacing bands, screen-by-screen copy,
tick-timbre-by-transport, and intro-copy-naming-sounds. The engineering
invariants embedded in the same passages were kept (compressed) in the
rewritten AGENTS.md; this file preserves the surrounding design narrative so
none of it is lost.

---

**The first-mix card's intent outlives a popover close; the wizard is a SHEET the popover cannot close under** (W3/W4, rehosted 2026-08-23). The CARD's intent (`btAlignmentPromptDeviceID`) survives rebuilds AND close/reopen — the backend's hold-silent outlives a click-away, so the offer must remount (`reconcileBTAlignmentPanels`, the diagnosis-panel idiom). The WIZARD is not in the card stack at all: it is presented with `presentAsSheet` on the panel (`AlignmentWizardViewController`, the Groups create-sheet idiom), so the host CANNOT `performClose` while it is up (AppKit refuses; the shell's R7 `hasAttachedSheet` and the menu-bar click policy already front-instead-of-close) and the old "survives popover close" contract is moot. An app-switch tuck-away (`hidesOnDeactivate`) hides host and sheet together and AppKit restores both; audio keeps running. A run ends only with a view-driven exit (Stop, Done, Esc) — and **Stop is on EVERY screen, the intro included** (there it is a corner row with no `Undo` behind it): a sheet carries no ✕, and with no reference to compare against Start is disabled, so without it the opening screen held no enabled control at all — or its target going un-live — gone, availability lost (a power-off keeps the row, greyed), or deselected, the predicate that also refuses a relaunch. A target lost under a LIVE sheet bows out in place (`showTargetLost`, "<name> went away." · Done) rather than vanishing the modal; the run itself still ends immediately. `reconcileBTWizardLiveness` still runs OUTSIDE the `isEffectivelyShown` gate, the one exception to hidden-means-idle: a tucked-away surface still has to reach a run whose speaker went away, and keep its picker current. `startBTAlignmentWizard` still stops the manual tick (one tick source). The wizard previews through the backend's LIVE delta path — never an engine rebuild, so each answer lands without a dropout. WHICH value it measures depends on the target: a BLUETOOTH row's run measures that speaker's own output LATENCY (persisted in `BTTrimStore`'s second map) and SUSPENDS the user's trim to 0 for the whole run — latency and trim are the same linear term in the delay, so a run judged with the nudge still on converges at `trueLatency + trim` and stores the workaround as the measurement. Keep writes latency AND trim 0 (the nudge stood in for exactly what was just measured); every other exit restores the store's value at `tearDownBTWizard`. The wide-open reference stays pinned through the RECEIPT: the tick's `false` edge no longer lowers it, `endBTWizardRun()` does, after the Keep write, so the timeline moves once and the user keeps hearing what they judged. The MAC's row still measures its sync offset (`onLocalTrimPreview` → `BTSyncedSink.applyTrimDelta`'s local twin). The two run in OPPOSITE directions — a larger latency feeds a speaker EARLIER, so a target heard first needs LESS of it, which is what `BTAlignmentWizardSession.invertsEstimate` carries. The wizard's ticks are ARMED by the backend once every participating sink is actually playing, not after a fixed preamble, and the stimulus tempo follows the estimator's stage (`onBTWizardTempo`). **The intro NAMES the two sounds, but only when the pair really makes two** (2026-08-24, `dev/notes/wizard-tick-stimulus-brief.md` §5.2): the tick's timbres are split by TRANSPORT, not by role — bright click on the Bluetooth fan-out, low knock on the engine feed (AirPlay + the Mac's own output) — so a Bluetooth target against the default Mac reference sounds different while Bluetooth-vs-Bluetooth plays one identical click on both sides. `BTAlignmentWizardSession.pairSoundsDiffer` (both sides' transports, the reference's read live because the user can swap it mid-run) gates `introCopyNamingSounds`; same-transport pairs keep `introCopy` verbatim, because promising a cue the run isn't giving is worse than saying nothing. The sentence names each side's sound from ITS OWN transport — a Mac target with a Bluetooth reference is the same sentence reversed — and the host is the only thing that knows a device's transport, so it passes both bits into the session. All three card actions release the backend hold; only "Not now" records — and that dismissal is FINAL, but silences ONLY the auto-prompt: the wizard stays reachable forever (⌥-click on the drawer's metronome button, or the BT row's "Align speaker…" context-menu item). One card at a time, but a second device's simultaneous offer QUEUES — its own hold untouched, only ITS card's resolution releases it — and mounts when the slot frees; never resolve a prompt the user hasn't seen. Every card/wizard interaction tests through REAL dispatch (`performClick` / `performActionForItem`), never state pokes.

**The wizard's estimator is a BAYESIAN POSTERIOR, and it proposes a value rather than running to a fixed end.** `BTAlignmentPosterior` keeps a probability curve over whole-ms offsets across the usable range, multiplies in each answer's likelihood under a fixed listener model (deliberately WIDER than a real listener, which is what keeps it unbiased inside ~10 trials — in TWO widths since 2026-08-24, a sharper `c = 4` / `λ = 0.06` for an ordinary run and the original `c = 6` / `λ = 0.12` for a LATENCY run, whose grid is twice as wide and still needs the breadth: `dev/notes/wizard-estimator-effectiveness-brief.md` §3.4), and asks next at whichever candidate level minimises expected posterior entropy. It is DETERMINISTIC — no RNG anywhere — so the same answers always produce the same questions, and `back()` refolds the belief from the flat prior instead of keeping undo states. Three consequences that are easy to get wrong: **(a)** "Both at once" is EVIDENCE, not a shrug — a monotonic staircase cannot use a non-monotonic answer, which is the whole reason the old constant-stimuli design needed blocks; **(b)** the run STOPS when the 95% credible interval's half-width reaches 8 ms, never at a fixed answer count, so there is no fraction of a run to report: `AlignmentStageView` draws the belief itself as light, and may WIDEN after a rejected proposal — honest, never clamp it monotone. It moves on ANSWERS only, never on the audible beat; **(c)** the prior is FLAT even on the zero-click path (a stored measurement opens on the PROPOSAL, a UI shortcut, not a seeded prior — an under-broad prior is the one thing the published advice says not to do). The proposal screen keeps the TICK RUNNING: the user judges by listening, and re-firing the gate costs a full re-anchor of every sink. Accepting IS keeping, and the sheet stays up on `.kept` so the row's chip can be watched flipping — flipping to the MEASUREMENT the run just printed, not to the nudge Keep zeroed (the chip's number is measurement + nudge; see the SharedUI folder's SYNC-control bullet). The two bow-outs are OPPOSITES and must stay distinguishable: `.unreachable` = the belief has piled up in the outermost margin of the range (the control cannot reach what the user is hearing), `.unsettled` = the interval stopped narrowing, too many answers, or a third rejected proposal — and only `.unsettled` offers "Set it by hand", which opens the row's SYNC drawer on the best guess FOCUSED BUT NOT COMMITTED (the drawer emits committed gestures only). Every screen is ONE fixed chassis — TITLE ROW, stage, readout — with only the band beneath changing, so a run never reflows. The stage never moves; the readout BELOW it collapses to zero height on the four screens that print no caption (`applyReadoutHeight`, driven off the SCREEN and never off the readout's string — the kept line arrives later, on the stage's lock cue), which is what lifts the intro's opening sentence out of the middle of the sheet. `AlignmentStageView.Rung` owns the readout's status WORD as well as the look (one constant per boundary; no thresholds in the view). **The top row is a plain sheet TITLE, not a nameplate** (owner ruling 2026-08-24, wizard-only — the mono-caps `applyMicroVoice` voice is retired HERE and stays everywhere else until roadmap 059 sweeps it): `Align <device name>` at `bodyEmphasized`/`label`, left-aligned on the stage plate's own left edge, with the click count as a quiet aside on its right — `Click n of about 15` / `About 15 clicks`, sentence case, `caption`/`inkSecondary`, never mono and never all-caps. The stage's in-plate NAME STAMPS follow the same One Case rule as everything else on this sheet (roadmap 059's foundational token change landed on main 2026-08-23, ahead of this branch's fork — `Tokens.Font.microLabelKern` is gone and `microLabel` is plain semibold, sentence case as authored): no forced uppercase, no kern. The right slot rides the title's FIRST BASELINE, never `.centerY` (the corner chips' rule — two sizes centred drop the smaller baseline). **The `usesSingleLineMode` trap survives verbatim and now applies to THREE labels**: the click count and the corner rows' `⌘Z`/`ESC` key chips. A label left multi-line publishes NO horizontal content-size constraint, so a slot pinned on ONE side lays out at the 4 pt empty-field bearing and is simply absent from the screen with nothing in the code reading wrong. Single-line mode CLIPS rather than truncates, so the TITLE additionally carries `.byTruncatingTail`, low horizontal compression resistance and a `<= clickCountLabel.leading` pin: the two slots hang off opposite edges of a plain container, and nothing else stops a long device name drawing straight THROUGH the click count (`test_titleSlotsAreClear`; the name gives way, the fixed-width chrome never does). A key chip aligns to its button's FIRST BASELINE, never `.centerY` — the chip's type is ~4 pt smaller, and centring two sizes drops the smaller baseline by that much, which reads as a subscript. The reference picker is INTRO-only (one candidate reads as plain text, none disables Start), and **a CHOICE is a FORM FIELD while a STATEMENT is a caption** (two owner live passes, 2026-08-24: the reference first "blends right into the background beside this huge CTA", then, raised to a body label around a regular pop-up inside the sentence, was the right direction but still not "an element you need to interact with"): the 2+-candidate case stops being a word in a sentence and becomes the macOS form field every Settings pane already taught the user — `Compare against` (`Tokens.Font.body` at full `label`, NO device name in it) on its own line above a `.large` stock `NSPopUpButton` pinned to `bodyMeasure` (400), the whole field standing off in its own `spacingBand`; the 0- and 1-candidate lines stay caption/`inkSecondary` with NO control mounted at all, because nothing on them can be clicked and a field would promise an affordance the screen doesn't have (`test_referenceLineIsRaised` pins all three halves of the picker case at once — label voice, `.large`, and the width constraint active at `bodyMeasure` — since round 1 proved the voice alone passes while the screen still reads as prose). Three things were tried and only this one held: a 400×44 bordered `well` row with a leading label and a trailing regular pop-up read as a control but dressed a band that ISN'T clickable as one (the label and the row's own inset do nothing), and giving that row the reference's identity rim was invisible — 1 pt of `partySignal` around 400 pt of ground is not a signal, and the identity rims belong to the answer plates where the user is choosing BETWEEN the two. Renders for all three: `dev/notes/wizard-v2-handoff/intro-cta-r2-{field,row,row-identity-rim}/`. The diagnosis was NOT that Start is too big: the 220×64 gold plate and the other screens are untouched, and the field being WIDER than the CTA is the point — form above, submit below, with gold and height carrying primacy. The readout under the stage ASKS the question (`Which clicked first? · <word>`); the interval is the stage's tooltip. **That line carries TWO voices and must keep them apart** — the question at `captionEmphasized`/`label`, the rung word at `caption`/`inkSecondary`, one attributed string. Set flat they read as one eight-word run of chrome and the ask vanishes into it; the readout cannot answer that by growing, because the plates are the hero. For the same reason the three plate titles all read as REPLIES to that question — two speaker names and "Both at once", never a statement about a different question — and the question screen's AX label is composed from those same four strings, so what VoiceOver asks and what the screen prints can never drift. The two answer plates are the screen's hero (236×88); the stage is a 132 pt strip that stamps the two names under the lights while armed, with the WIRE ON THE PLATE'S MIDLINE (`wireYFraction` 0.5, owner ruling 2026-08-24 — at 0.62 the halo and the name stamps crowded the bottom rim while a 27 pt band sat empty above the lights). It is a constant of the plate's height, so the wire never moves between screens. Identity colour names WHICH speaker, never state — green `syncSignal` target, magenta `partySignal` reference, Deep companions in light — resolved by the VIEW per appearance — carrying the plate RIM's alpha inside the tint (FULL-strength electric on dark, 0.9 Deep on light — owner ruling 2026-08-23 over spec §2.1's 0.45, which measured olive/mauve at 45% of the lights' chroma); the cell restores full alpha for the keycap glyph — and handed to `AlignmentPlateCell`, a DRAWING-only cell swap that must keep `isBordered = true` (borderless discards `drawFocusRingMask`, openradar 29465363) and whose button zeroes `alignmentRectInsets` (the `.push` bezel's ~7 pt insets otherwise inflate a 220 pt plate to 234 and collapse every row gap); an `NSButtonCell`'s `attributedStringValue` is its STATE, never its title — measure `attributedTitle`; gold stays the "is it live" voice, on the screen's one primary plate. **That primary plate is BRIGHT gold with BLACK ink, the same in both appearances** (owner ruling 2026-08-24, replacing `goldCTA` + white — which is the DEEPENED gold built for white ink and read as dark mustard on screen). `AlignmentPlateCell.primaryFillColor` resolves `Tokens.Color.gold` ONCE under `.darkAqua` and pins that value in light too, so there is one CTA colour rather than two; it is still READ from Tokens, so the accent dial and Increase Contrast reach it. Fill, both bevel lips and the rim all derive from that one value; the title and the keycap chip both take `Tokens.Color.inkOnGold` (black — measured 11.4:1 on Full-gold dark, 13.1:1 Increase Contrast, 7.9:1 on the Subtle dial; pinned in `AlignmentTokenContrastTests`). `goldCTA` is untouched and still owns the Setup finale's CTA. **A `.trailing` plate's title is centred in the WHOLE PLATE**, with the keycap chip overlaying the trailing edge without displacing it: `titleRect` takes the chip's reserve off BOTH sides, which puts the box's centre on the plate's centre AND still stops a long device name running under the glyph. Centring the title in only the space beside the chip — what it used to do — sat every CTA's word ~23 pt left of the midline on a symmetric plate. **Colour rule (Alec, 2026-08-23): gold is the app's primary colour, always; `syncSignal`/`partySignal` are sanctioned ONLY inside this wizard — using either anywhere else requires asking Alec first with a clear rationale.** The VIEW owns the key map (←/→/Space each a real `performClick` on its plate, ⌘Z Undo, Esc Stop, Return the default plate), and it is SPLIT the way AppKit's own dispatch splits it. **TRAP: `performKeyEquivalent(with:)` is NOT a live path for UNMODIFIED keys** (live bug, build wizardv6 — ←/→ did nothing on the question screen while the suite was green, because the tests called `performKeyEquivalent` directly: this repo's "tests bypass AppKit dispatch" trap). Probed against real dispatch: `NSApp.sendEvent` runs the key-equivalent pass down the key window's view tree only for a MODIFIED key (⌘Z traverses canvas → wizard view → plates); a plain ←/→/Space/Esc/Return skips that pass entirely and is delivered to the window's FIRST RESPONDER as an ordinary `keyDown`. So ⌘Z is the only case left in `performKeyEquivalent`; every unmodified key rides `keyDown(with:)`, which means the view must BE the first responder — `acceptsFirstResponder` plus a `makeFirstResponder(self)` in `viewDidMoveToWindow`, the SECOND half of the same live bug: the old `initialFirstResponder = self` assignment stood alone, and AppKit's become-key pass SKIPS an `initialFirstResponder` that declines the job (probed on a real sheet — the WINDOW kept first responder), while a direct `makeFirstResponder` call ignores `acceptsFirstResponder` entirely. Both lines are load-bearing, for different halves. Focus is re-claimed at the end of every `render` because a screen rebuild that tears out a focused plate drops focus back to the window, where an arrow dies. Return is deliberately UNHANDLED and falls through `super.keyDown` up the chain to the window's default-button dispatch, which fires the plate carrying `keyEquivalent = "\r"` — swallowing it in `keyDown` would kill the default plate. Both entry points stand aside for a live field editor. **SECOND TRAP, same map, live build wizardv7: "unmodified" is NOT `modifierFlags.intersection(.deviceIndependentFlagsMask).isEmpty`.** AppKit stamps every ARROW keyDown with `.function` + `.numericPad`, and both bits live inside that mask — so with the first responder correct and the dispatch correct, ←/→ were still rejected by the guard while Space, Esc, Return and ⌘Z all worked (probed via `NSEvent(cgEvent:)` on a real ←: deviceIndependent `0x20a00000`, against `0x20000000` for Space/Esc/Return). The question a key map may ask is "is the USER holding a modifier?" — `BTAlignmentWizardView.heldModifiers`, i.e. command/option/control/shift, Caps Lock deliberately excluded so it can't kill the arrows — and BOTH entry points plus the `test_sendKey` seam ask it that way. Tests drive the unmodified keys through a real `NSWindow.sendEvent` (`hostSheetInWindow`) carrying AppKit's OWN flags for the key (`appKitFlags(forKeyCode:)` — an arrow synthesised bare is a press no keyboard makes, and that is how the dead map shipped green twice), never `performKeyEquivalent` — and `AlignmentWizardViewController.dismissSilently` therefore gates on `presentingViewController`, not "am I in a window", because `dismiss` on an unpresented controller raises `NSInternalInconsistencyException`. **The two lights are LIVING RINGS ported from the marketing site's emitter component** (`src/scripts/fields/emitters.js` at `house-bg.js`'s saved values — wobble 0.03, wobbleRate 0.5, squash 1.12, per-light seed `f·6.13 + 1.7`, breathing swell as the glow envelope; the field's outward travel and orbit drift are deliberately NOT ported, because a light's position is DATA): a 30 fps `CADisplayLink` rewrites each ring's path and each light's opacity per frame, and it rides the exact same gate as the idle breathing — so a rung that does not breathe (`locked` above all, where stillness is the reward) is also a rung that does not waver, and under Reduce Motion, `HeadlessRuntime`, or off screen the stage draws its PINNED phase, where the wobble term is zero and the swell factor is exactly 1, which is what keeps the renders and goldens byte-deterministic; the squash is a SETTLED property and renders at pinned phase too, and the swell is remapped from the emitter's ±43 % to ±6 % of the rung's own opacity so brightness still encodes certainty rather than crossing a rung boundary. **The lights are drawn 1.8× the spec §5 table's sizes, and `stageHeight` is 132 rather than 112 as the price of it** (owner ruling 2026-08-24, after the port shipped): the ported wobble is ±3 % of the RADIUS, so on the spec's 9–20 pt rings the wavefront's whole peak-to-peak travel was 1.1–2.4 Retina pixels and the life that had just been ported could not be seen. Radii are 36/32/25/20/16 (armed → threshold), halos 106/96/76/60/46, travel 1.9–4.3 px, line widths ×1.25–1.33 not ×1.8 — a stroke scaled with the radius reads as a drawn hoop rather than a lit edge. Three things move together and none is a free multiply: **the halos scale with the rings** or the glow stops being glow, which is what forces the taller plate; **the plate's height is the SHEET's height** (`chassisHeight` reads `stageHeight` 1:1), so every screen grew 20 pt and the stage went from 27 % of the question sheet to 30 % — the ratio the answer plates' primacy actually rests on, and a 2.2× scale wanting 152 (33 %) is where the stage becomes the hero instead; and **the ladder's adjacent-rung gaps grew with everything else**, 4/7/5/4 pt where they were 2/4/3/2, so each certainty step is twice as legible while its ratio to the wobble at that size is unchanged. That last part is the constraint, not a bonus: RADIUS is how the ladder encodes certainty, so any future rescale must keep the gaps ahead of the wobble at the same size — and must NOT close the spread by growing the tight rungs toward the wide ones (measured: at 132 pt the tight rungs then read as the light retreating into an empty box exactly when the user is most invested). Reduce Motion, headless and pinned phase are untouched by all of this — the renders stay byte-deterministic.
